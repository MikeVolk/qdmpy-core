branch develop @ 6a5a6c6 · 2026-07-03 · focus: maintainability · usability · extensibility

Each candidate below is a deepening opportunity: a refactor that puts more behaviour behind a smaller interface. Vocabulary: a module is an interface plus an implementation; it is shallow when the interface is nearly as complex as the implementation; a seam is a place where behaviour can be swapped without editing code in place. Candidates that overlap an existing draft QEP say so — implemented QEPs are treated as settled decisions and are not re-litigated.

1 · A fit backend seam: FitBackend protocol

Strong

Files: fitting/manager.py · measurement.py · measurement_workflows.py · fitting/models.py · settings.py

Problem

The GPU dependency is not a seam — it is a scattered hard conditional. is_pygpufit_available() is checked in manager.py:80, manager.py:290, manager.py:619, manager.py:708, measurement_workflows.py:170 and measurement_workflows.py:327, and a gpu_available: bool flag is hand-threaded through every public signature from Measurement.fit_odmr() down. The actual pygpufit.gpufit.fit_constrained call is inlined mid-method (manager.py:640). Consequences: the documented custom-model contract (models.py:206, "model_id = -1 # CPU-only") is dead — a pure-Python model crashes in gpufit; and every fit-adjacent test must monkeypatch internals (46 mock sites in test_measurement.py, 28 in test_refit.py).

Solution

Define a narrow FitBackend protocol — roughly fit(data, freq_ghz, initial_params, constraints, constraint_types, model) → RawFitOutput — and put every adapter behind it: GpufitBackend (current code), a ScipyBackend for pure-Python models and GPU-less machines, and a trivial fake for tests. FitManager takes the backend by constructor injection and resolves the default once (gpufit if importable, else scipy). Delete the gpu_available parameter from all seven signatures and the duplicated DependencyError blocks.

Benefits

  • Locality: "can we fit?" is decided in exactly one place — backend resolution — instead of six.
  • Leverage: two real adapters (gpufit + scipy) make this a genuine seam, revive the custom-model contract, and let the whole library run on machines without CUDA.
  • Tests: the interface becomes the test surface — Measurement/refit/folded tests pass a fake backend instead of patching module internals; the mock-heavy suites shrink to behaviour assertions.

Existing QEP: none covers this. Deletion test: removing the scattered checks concentrates complexity into one adapter — it reappears in exactly one place, which is the point.

2 · One fit pipeline inside FitManager

Strong

Files: fitting/manager.py (794 lines) · odmr/folding.py

Problem

Three entangled issues. (a) fit() (manager.py:269-382) does nine jobs in one method: validate, auto-resolve model, flatten, guess, per-range dispatch, transpose, build the parameter dict, compute quality metrics, construct FitResult. (b) fit_folded() (manager.py:680-794) re-derives the folded fit inputs by hand (D_ZFS + delta_f, expand_dims) even though FoldedODMR.to_fit_inputs() (folding.py:185) exists and is already used by the refit path — one consumer uses the seam, the other bypasses it — then constructs a second FitManager inside itself (manager.py:776). (c) The class claims to be "stateless between calls", but _apply_mt_center_window_for_range() (manager.py:384) mutates the shared ConstraintManager mid-fit, so one fit() call silently changes the constraints seen by the next.

Solution

Adopt draft QEP-FIT-003 (stage decomposition) and QEP-060 (path unification) together, with two additions: fit_folded() must consume FoldedODMR.to_fit_inputs() and become pure data-preparation in front of the one pipeline; and per-range constraint windows become local values passed into the range fit, not mutations of shared state. Extract the ~110 lines of freq_cutoff dict parsing (manager.py:140-254) into a small frozen FreqCutoff value object that validates itself.

Benefits

  • Locality: folded and non-folded fits can no longer drift — there is one place where model resolution, constraints and result assembly happen.
  • Depth: FitManager's interface stays the same (fit, fit_folded) while the implementation gets simpler — the definition of deepening.
  • Tests: each stage (prepare → guess → dispatch → assemble) is independently testable; the stateless claim becomes true and testable.

Existing QEPs: FIT-003 + 060 are drafts pointing here; this candidate endorses them and adds the to_fit_inputs() reuse, the self-construction removal, and the hidden-mutation fix, which neither draft itemizes.

3 · Collapse the wrapper chain; a FitOptions value object

Strong

Files: measurement.py · measurement_workflows.py · __init__.py

Problem

A fit call descends four layers: Measurement.fit_odmr → fit_measurement_odmr → build_fit_manager → FitManager.fit. The middle two are pass-throughs: build_fit_manager (workflows.py:180-197) and build_qdm_result (workflows.py:200-210) are 3-line thunks re-spelling constructor calls — they fail the deletion test outright. The kwarg tuple (constraints, freq_cutoff, settings, gpu_available) is copy-pasted across seven signatures (fit_odmr, fit_folded_odmr, refit_outliers and all four workflow functions), so adding one fit option means editing seven parameter lists in lockstep. load_measurement_folder_data injects listdir, image_loader and an unset_sentinel as parameters (workflows.py:69-80) — pure-function extraction for testability, with the real behaviour still only reachable through the whole chain (no locality gained). The mock density in test_measurement.py (46 sites) is the direct cost.

Solution

Introduce one frozen FitOptions value object (model, constraints, freq_cutoff, refit settings) that travels as a single argument, then delete the thunks and fold the two genuinely load-bearing workflows (load_measurement_folder_data, refit_measurement_result) into their only callers or keep them as the single implementation with Measurement methods as documented one-liners. With candidate 1 in place, the injected-callable ceremony disappears because tests inject a backend/loader instead of listdir.

Benefits

  • Leverage: a new fit option = one field on FitOptions, not seven signature edits.
  • Locality: one obvious place where a fit is configured; the docstring schema for freq_cutoff stops being repeated in six places.
  • Usability: users see one canonical path (load → fit_odmr → QDMResult) instead of a workflows module that looks like a second API.

Existing QEP: 057-API (draft) covers naming/docs drift but not the wrapper-layer thinness or the kwarg-tuple duplication.

4 · Models that fully describe themselves

Strong

Files: fitting/models.py · fitting/guesser.py · fitting/guess.py · odmr/folding.py · fitting/result.py

Problem

The @ModelRegistry.register decorator looks open/closed, but model knowledge leaks into four other modules: guesser.py:136-147 branches on n_peaks == 3 / == 2 with hardcoded hyperfine width-correction factors; folding.py:69-73 keys a _CENTROID_POWER dict on model-name strings (unknown models silently get a default); guess.py:173-180 matches models by peak count, so two models with equal n_peaks are indistinguishable to auto-detection; result.py:121-159 probes parameter-name strings (width_0 vs width…). Adding an ESR model is documented as "subclass + register" but actually touches ≈3 files, and the registry itself is a class-level mutable global (models.py:382) shared across tests.

Solution

Move every model-specific fact onto Model as declared attributes: hyperfine_splitting_ghz, guess_width_correction, centroid_power, and a detection_signature the auto-detector consults. Guesser, folding and detection then read the model instead of switching on it — the registry becomes the only place a model is named. Combine with draft QEP-FIT-005's registry cleanup (instance-based or resettable registry, drop the _param_idx aliases resonance/mean_contrast at manager.py:586-587).

Benefits

  • Extensibility: a new model is genuinely one file; with candidate 1's scipy backend it is also fittable without CUDA kernels.
  • Locality: physics constants (AHYP factors, centroid powers) live next to the model they describe instead of in consumer branches.
  • Tests: model behaviour tested through the model's own interface; registry resettable per test.

Existing QEPs: QEP-005 (implemented) started this — parameter names/units already live on Model; FIT-005 (draft) covers the registry global but not the guesser/folding leaks. This extends both without contradicting either.

5 · One owner for fit-result serialization

Worth exploring

Files: fitting/result.py (~250 lines of I/O) · io/npz.py · io/qdm.py · result.py

Problem

Three codecs for the same arrays coexist: FitResult.save_results/load_results (NPZ, plus legacy-pickle migration, fitting/result.py:547-804); io/npz.py, which reaches into FitResult privates (_build_save_dict at npz.py:38, _from_npz at npz.py:73); and io/qdm.py (HDF5), which re-implements cache injection. Both container classes claim "pure data container — all I/O is in qdmpy.io" (result.py:8, fitting/result.py:44) while owning save/load. The stated boundary is fictional: a format change touches FitResult privates plus two io modules.

Solution

Give FitResult one small public codec interface — to_payload() → dict[str, NDArray] + meta and from_payload(...) — and make qdmpy.io the only module that touches files. NPZ and HDF5 become two adapters over the same payload (two adapters = the seam is real). FitResult.save_results and QDMResult.save/load stay as documented one-line conveniences delegating to io. Quarantine legacy-pickle migration in io/legacy.py with a removal date.

Benefits

  • Locality: a format change = one payload definition + the affected adapter.
  • Honesty: the "pure container" docstring becomes true; io stops depending on privates.
  • Tests: round-trip tests target the payload contract once, not three codecs.

Existing QEPs: 051-ARCH (implemented) started the split; 056-IO and 057-API (drafts) restate the goal. This is the concrete mechanism both drafts are missing.

6 · Pluggable loaders at the front door

Worth exploring

Files: odmr/io.py · measurement_workflows.py:115 · __init__.py

Problem

BaseLoader is a clean seam and ODMRData.from_loader() accepts any loader — but the only ergonomic entry points, qdmpy.load() and Measurement.from_folder(), hardcode MatlabLoader(str(folder)) (workflows.py:115). A user with a new format writes one loader file and then must abandon the front door entirely, hand-assembling ODMRData → ODMR → Measurement. One adapter behind the seam = today it is only a hypothetical seam. Separately, MatlabLoader.load() is a 105-line method carrying # noqa: C901, PLR0912, PLR0915 (odmr/io.py:65) with the load-bearing y-axis flip buried mid-method.

Solution

Add loader: BaseLoader | None = None to load()/from_folder() (default: MatlabLoader), making the existing seam reachable from the path users actually call. Optionally register loaders by detection (a loader says whether it recognises a folder), giving a second adapter and a real seam. Decompose MatlabLoader.load() along its natural stages (discover files → read mat → parse frequencies → reshape/orient) per draft QEP-ODMR-003.

Benefits

  • Extensibility: new instrument format = 1 file and the front door still works.
  • Tests: a tiny in-memory loader lets Measurement.from_folder-level tests drop the listdir/sentinel injection ceremony.

Existing QEP: ODMR-003 (draft) hardens MatlabLoader internals but does not wire loaders to the entry point.

7 · One processor-pipeline framework

Worth exploring

Files: odmr/processors.py · field_processing.py

Problem

The same concept — "an ordered list of steps, each mapping data → new data" — is implemented twice with divergent contracts. The ODMR side has three overlapping abstractions: a Processor Protocol claiming "no base class needed" (processors.py:24), a BaseProcessor ABC (:77), and a hardcoded ProcessorSpec union for serialization (:218-225) — so a Protocol-only custom processor passes type checks but fails from_config() round-tripping. The field side (field_processing.py) has a fourth framework with a different API (.add() vs .add_processor(), no serialization at all). Extension cost is asymmetric: ODMR processor = 2 edit points; field processor = different rules entirely.

Solution

One generic Pipeline[T] with a registry-driven serialization scheme (a processor registers its config tag; the union is derived, not hand-maintained), used by both ODMR spectra and field maps. Drop the Protocol-vs-ABC duality: one base with process(data: T) → T, to_config(), from_config(). This also feeds draft QEP-049's pipeline.toml — a single schema instead of two.

Benefits

  • Extensibility: one rule for adding a step anywhere in the system; custom processors serialize without editing a union.
  • Leverage: pipeline features (logging, timing, config round-trip) written once serve both domains.

Existing QEP: ODMR-002 (draft) fixes the ODMR-side triplication; the cross-domain unification and registry-derived union go beyond it.

8 · Downward-only layering & delegation hygiene

Speculative

Files: plotting/* · fitting/result.py · result.py · odmr/analysis.py · utils.py · settings.py

Problem (a bundle of smaller, related frictions)

  • Layer inversion: ~30 inside-function from qdmpy... imports exist mostly so lower layers can call up into plotting (fitting/guess.py:168, fitting/result.py:617-633, folding.py:210, odmr/manager.py:160); meanwhile plotting reaches into fitting privates (plotting/odmr.py:426 imports _relative_prominence).
  • Shallow delegation: QDMResult hand-writes ~18 one-line forwards to FitResult (result.py:87-171) — every new FitResult property must be mirrored or silently missing.
  • Physics duplication: B111 math lives in both fitting/result.py:330-419 and odmr/analysis.py:35-83, and has already diverged once (per draft QEP-FIT-004).
  • Catch-alls: utils.py mixes string formatting, coordinate transforms and math; defaults like fluorescence_correction=0.2 and pixel_spacing=4e-6 are re-declared in 3 layers each; the load() default model is "auto" while FitManager's is "ESR14N".

Solution

Keep the convenience methods (users like result.plot()) but make plotting register itself: plotting depends downward on result types; result classes expose a single plot(kind=...) that dispatches through a small registry plotting populates on import. Replace QDMResult's forwarding block with __getattr__ delegation plus an explicit __dir__. Make odmr/analysis.py the single B111 implementation, called by FitResult (per draft QEP-FIT-004). Declare shared defaults once in constants.py/settings and reference them everywhere. Split utils.py by domain. These are individually small; bundled because each is a "where does this live?" answer that pays off in navigability more than behaviour.

Benefits

  • Locality: the import graph becomes a DAG you can explain in one diagram; B111 sign fixes land once.
  • Maintainability: new FitResult surface propagates to QDMResult automatically; default changes are one-line edits.

Existing QEPs: FIT-004 (draft), CORE-003 (draft) cover parts. Marked speculative because the mechanism choices (registry vs. protocol vs. accept-the-cycle) genuinely need discussion, and __getattr__ delegation trades IDE discoverability for zero drift.

Top recommendation: start with #1 — the FitBackend seam

Three reasons. First, it is the only Strong candidate no existing QEP covers — the others already have draft momentum you can activate any time. Second, it is the keystone for the rest: candidate 2's pipeline unification is far easier to verify when a fake backend makes the pipeline testable end-to-end without a GPU; candidate 3's kwarg collapse deletes the gpu_available plumbing this seam makes obsolete; candidate 4's pure-Python custom models are only viable once a CPU backend exists. Third, it converts the most expensive ongoing cost in the repo — the ~85 monkeypatch sites across the fit-adjacent test suites — into ordinary dependency injection, which is the difference between tests that assert wiring and tests that assert physics.

Suggested sequencing afterwards: #2 (one pipeline, activating QEP-FIT-003 + QEP-060) → #3 (wrapper collapse + FitOptions) → #4 (self-describing models). #5–#8 are independent and can ride along opportunistically.
