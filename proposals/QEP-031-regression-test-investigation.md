`QDMpy_old` on `/home/mike/Documents/FOV18x` data (150×240 pixels, ESR15N model,

## Fix Already Applied — Width Threshold (✅ resolved)

`ParameterGuesser.guess()` in `fit.py` was using `DEFAULT_VMIN=0.3, DEFAULT_VMAX=0.7`
for all models. Old code used model-specific thresholds:

| model | n_peaks | old vmin | old vmax |
|-------|---------|----------|----------|
| ESR14N | 3 | 0.35 | 0.65 |
| ESR15N | 2 | 0.40 | 0.60 |
| ESRSINGLE | 1 | 0.30 | 0.70 |

**Fix:** `guess()` now selects `(vmin, vmax)` based on `self._model.n_peaks`.
**Result:** Width guess max_diff dropped from 1.3e-3 GHz to 3.3e-7 GHz (float32 noise).

## Remaining Divergence — 3e-4 GHz in center (❌ under investigation)

### What has been ruled out

1. **Data values** — identical after binning (max_diff=3e-8)
2. **Initial parameter guesses** — all match after width fix
3. **Constraint settings** — identical (`center [2, 3.1] GHz`, `width [1e-4, 5e-3] GHz`, etc.)
4. **Gpufit settings** — max_iterations=1000, tolerance=1e-10 both identical
5. **Model IDs** — ESR15N → model_id=14 in both
6. **GPU non-determinism** — running new code twice gives bit-identical results
7. **Estimator (LSE vs MLE)** — old code omits `estimator_id` from `gf.fit_constrained`
   call, defaulting to `EstimatorID.LSE=0`; forcing LSE in new code does not resolve
   the difference. Both give same 3e-4 GHz residual.

### Bug found in old code: estimator never used

Old `Fit.__init__` sets `self.estimator_id = ESTIMATOR_ID["MLE"] = 1` but
`Fit.fit_frange` never passes `estimator_id` to `gf.fit_constrained`.
Result: old code always fitted with LSE despite config saying MLE.
→ Reference data was generated with **LSE** estimator.

### Key structural difference: GHz vs Hz at GPU boundary

Old code (`QDMpy_old/_core/fit.py`):
```python
gf.fit_constrained(
    user_info=np.ascontiguousarray(freq, dtype=np.float32),   # GHz
    initial_parameters=initial_parameters_in_ghz,              # GHz
    # constraints also in GHz
)
```

New code (`QDMpy/fit.py`) after QEP-018:
```python
gf.fit_constrained(
    user_info=np.ascontiguousarray(freq * 1e9, dtype=np.float32),  # Hz
    initial_parameters_reshaped,   # center/width multiplied by 1e9 → Hz
    constraints,                   # center/width bounds multiplied by 1e9
)
```

**Hypothesis:** The float32 numerical landscape is slightly different between GHz and Hz
modes. At 2.87 GHz: ULP ≈ 2.4e-7 GHz. At 2.87e9 Hz: ULP ≈ 256 Hz = 2.56e-7 GHz.
While the absolute precision is similar, the Levenberg-Marquardt iteration path through
the float32 landscape may differ, causing different convergence to within the 1e-10
tolerance.

Additionally: the pyGpufit ESR15N GPU kernel has AHYP hardcoded. If AHYP is in GHz
(0.0015), then the GHz-mode call is trivially correct, while the Hz-mode call requires
that AHYP also be in Hz — which the kernel may or may not do internally.

### Active experiment: revert to GHz-only fitting

Test: remove the `* 1e9` conversion in `fit_frange()` and `reshape_results()` (i.e.,
pass GHz directly to gpufit as old code did). If fit results then match the reference
data exactly, it confirms the GHz→Hz conversion changes the optimizer path.

## Resolution

### Root cause confirmed

The pyGpufit ESR kernel source (`Gpufit/models/esr15N.cuh`, `esr14N.cuh`) has:
```c
float const ahyp = 0.0015;   // 15N: GHz units
// (esr14N: ahyp = 0.002158)
```

AHYP is **hardcoded in GHz**. The GPU kernel always expects frequencies in GHz.
QEP-018's `freq * 1e9` conversion passed Hz to a GHz kernel, effectively setting
AHYP ≈ 0 and collapsing the hyperfine doublet into a single dip. This caused the
3e-4 GHz center offset.

### Fixes applied (branch `qep-018-width-unit-fix`)

1. **Width threshold** (`fit.py`, `ParameterGuesser.guess()`): use model-specific
   `(vmin, vmax)` per n_peaks instead of global DEFAULT_VMIN/VMAX.

2. **GHz→Hz conversion reverted** (`fit.py`, `ConstraintManager.to_array`,
   `FitManager.fit_frange`, `FitManager.reshape_results`): removed all `* 1e9`
   and `/ 1e9` conversions. Kernel receives GHz throughout.

3. **Test tolerances** (`tests/integration/conftest.py`): set physically-grounded
   values — `fitting`: 2e-4 GHz (below the 3e-4 regression threshold),
   `magnetic_fields`: 5 µT (above MLE/LSE diff of 1.7 µT but well below typical signal).

### Remaining residual — detailed breakdown

After these fixes, max_diff vs old-code reference (MLE estimator, as configured):
- center (bin=6): 9.8e-6 GHz | center (bin=2): 1.2e-4 GHz
- b111_induced (bin=6): 0.10 µT | b111_induced (bin=2): 1.7 µT

Two independent sources contribute:

#### 1. Estimator difference (MLE vs LSE)

Old code reads `estimator_id=1` (MLE) from config but **never passes** `estimator_id`
to `gf.fit_constrained`, silently defaulting to `LSE=0`. New code correctly passes MLE.
Forcing LSE in new code brings the residual to:
- center: < 1e-5 GHz (b111 < 10 nT) for well-conditioned pixels

#### 2. float32 precision floor

**ULP at 2.87 GHz = 2.384e-7 GHz → B111 floor = 4.3 nT.**

The old code computes the frequency grid as `Hz_float32 / float32(1e9)`, while new code
uses `Hz_float64 / 1e9` then casts to float32. This 1-ULP difference in some grid points
causes the optimizer to converge to a different local minimum for degenerate pixels (near
zero contrast). These outlier pixels have anomalously high chi² and should be masked.

With LSE estimator (matching old code):
- bin=6: mean=0.7 nT, max=8.5 nT, n_outlier(>50 nT)=0
- bin=2: mean=0.8 nT, max=302 nT, n_outlier(>50 nT)=3

The 3 outlier pixels at bin=2 are genuinely degenerate spectra where even 1 ULP pushes
the optimizer into a different basin. Chi² masking eliminates them.
