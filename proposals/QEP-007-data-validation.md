## QEP-011 Impact

QEP-011 introduced xarray `DataArray` with named dimensions `(polarity, freq_range,
y, x, freq_idx)`, which provides implicit structural safety — operations using
`dim=` arguments and named indexing will fail clearly on dimension mismatches.
However, `ODMRData.__init__()` still performs no explicit validation. A user can
pass an xarray DataArray with wrong dimension names, missing coordinates, or
invalid dtypes and get cryptic errors downstream.

## Motivation

`ODMRData.__init__()` accepts any `xr.DataArray` without validation. While xarray's
named dimensions provide better implicit safety than raw numpy arrays, bad data
(wrong dimension names, missing `freq_ghz` coordinate, non-numeric dtype) still
causes cryptic errors deep in the fitting pipeline.

Example failure chain:
1. User constructs a DataArray with wrong dimension names
2. `ODMRData` stores it without complaint
3. `FitManager` tries to access `.sizes['freq_idx']` and gets a `KeyError`
4. Or worse: silently produces wrong results if dimensions happen to match by size

Validating at the boundary (data ingestion) catches errors early with clear
messages.

### Why Pydantic

The original proposal rejected Pydantic, citing limited xarray/numpy support and
overhead on multi-GB arrays. Revisiting this decision:

1. **Pydantic v2 supports `arbitrary_types_allowed`** — xr.DataArray and NDArray
   fields work natively with `ConfigDict(arbitrary_types_allowed=True)`.
2. **Validation overhead is one-time at construction** — a few isinstance/dim checks
   on construction are negligible compared to GPU fitting. Pydantic does not copy or
   serialize the arrays; it only validates the field types and runs validators.
3. **Project already depends on pydantic + pydantic-settings** — no new dependency.
   Settings module shows the pattern works well.
4. **Declarative validation** — `@field_validator` is cleaner and more maintainable
   than manual `_validate_data()` static methods scattered across `__init__`.
5. **Typed metadata models** — replace loose `dict[str, Any]` metadata with typed
   Pydantic models that are validated at construction.

## Specification

### Design Approach

Use Pydantic BaseModel for data containers (`ODMRData`, `FitResult`) where the class
is primarily a validated data holder. Keep `FitManager` as a regular class because it
is heavily stateful and mutable — add Pydantic validation at its construction
boundary only.

### 1. ODMRData as Pydantic BaseModel

Convert `ODMRData` to a Pydantic `BaseModel` with field validators:

```python
from pydantic import BaseModel, ConfigDict, field_validator, model_validator

EXPECTED_DIMS = ('polarity', 'freq_range', 'y', 'x', 'freq_idx')

class ODMRData(BaseModel):
    model_config = ConfigDict(arbitrary_types_allowed=True)

    data: xr.DataArray
    metadata: dict[str, Any] = Field(default_factory=dict)

    @field_validator('data')
    @classmethod
    def validate_data_array(cls, v: xr.DataArray) -> xr.DataArray:
        if not isinstance(v, xr.DataArray):
            msg = f'ODMR data must be an xr.DataArray, got {type(v).__name__}'
            raise DataValidationError(msg)
        if v.dims != EXPECTED_DIMS:
            msg = (
                f'ODMR data must have dims {EXPECTED_DIMS}, got {v.dims}'
            )
            raise DataValidationError(msg)
        if not np.issubdtype(v.dtype, np.number):
            msg = f'ODMR data must be numeric, got dtype {v.dtype}'
            raise DataValidationError(msg)
        if 'freq_ghz' not in v.coords:
            msg = 'ODMR data must have a freq_ghz coordinate'
            raise DataValidationError(msg)
        return v

    # Existing properties (scan_dimensions, frequencies, numpy, shape) preserved
    # Existing classmethods (from_loader, from_numpy) preserved — they call cls(...)
    # which triggers Pydantic validation automatically
```

**What changes:**
- `ODMRData` inherits from `BaseModel` instead of `object`
- `__init__` is generated by Pydantic — same signature `(data=..., metadata=...)`
- `@field_validator('data')` replaces the manual `_validate_data()` static method
- `from_loader()` and `from_numpy()` classmethods stay as-is (they call `cls(...)`)
- Existing `@property` methods (`scan_dimensions`, `frequencies`, etc.) work
  unchanged on Pydantic models

**What does NOT change:**
- Public API — `ODMRData(data=da)` and `ODMRData.from_numpy(...)` work identically
- Properties — Pydantic BaseModel supports `@property` methods
- Memory — Pydantic stores the xr.DataArray reference, no copy

### 2. FitResult as Pydantic BaseModel

Convert `FitResult` to a Pydantic `BaseModel` with validated fields:

```python
from pydantic import BaseModel, ConfigDict, Field, PrivateAttr, field_validator

class FitResult(BaseModel):
    model_config = ConfigDict(arbitrary_types_allowed=True)

    parameters: dict[str, NDArray]
    scan_dimensions: tuple[int, int]
    pixel_spacing: float = Field(gt=0)
    model_name: str
    metadata: dict[str, Any] = Field(default_factory=dict)

    # Private attributes for caches (excluded from model schema)
    _b_field_cache: NDArray | None = PrivateAttr(default=None)
    _delta_resonance_cache: NDArray | None = PrivateAttr(default=None)
    _b111_cache: tuple[NDArray, NDArray] | None = PrivateAttr(default=None)

    @field_validator('scan_dimensions')
    @classmethod
    def validate_scan_dimensions(cls, v: tuple[int, int]) -> tuple[int, int]:
        if v[0] <= 0 or v[1] <= 0:
            msg = f'scan_dimensions must be positive, got {v}'
            raise DataValidationError(msg)
        return v

    @field_validator('parameters')
    @classmethod
    def validate_parameters(cls, v: dict[str, NDArray]) -> dict[str, NDArray]:
        if not v:
            msg = 'parameters dict must not be empty'
            raise DataValidationError(msg)
        return v

    # All existing properties and methods preserved unchanged
```

**What changes:**
- `FitResult` inherits from `BaseModel` instead of `object`
- `pixel_spacing` gets automatic `> 0` validation via `Field(gt=0)`
- `scan_dimensions` validated for positive values
- `parameters` validated as non-empty
- Cache attributes use `PrivateAttr(default=None)` instead of regular attributes
- `__init__` generated by Pydantic with same signature

**What does NOT change:**
- All properties (`centers`, `linewidths`, `contrasts`, `b111`, etc.)
- All methods (`save_results`, `load_results`, `calculate_b_field`, etc.)
- Public API — identical constructor signature

### 3. FitManager Input Validation

`FitManager` stays as a regular class (too stateful for BaseModel). Add boundary
validation at the top of `__init__`:

```python
class FitManager:
    def __init__(self, data: xr.DataArray, frequencies: NDArray, ...):
        self._validate_inputs(data, frequencies)
        # ... rest of existing __init__

    @staticmethod
    def _validate_inputs(data: xr.DataArray, frequencies: NDArray) -> None:
        if data.size == 0:
            msg = 'Cannot fit empty data array'
            raise DataValidationError(msg)

        freq_2d = np.atleast_2d(frequencies)
        n_freq_data = data.sizes.get('freq_idx', data.shape[-1])
        n_freq_array = freq_2d.shape[-1]
        if n_freq_data != n_freq_array:
            msg = (
                f'Data freq_idx dimension ({n_freq_data}) must match '
                f'frequency count ({n_freq_array})'
            )
            raise DataValidationError(msg)

        MIN_FREQ_POINTS = 10
        if n_freq_array < MIN_FREQ_POINTS:
            msg = (
                f'Need at least {MIN_FREQ_POINTS} frequency points '
                f'for fitting, got {n_freq_array}'
            )
            raise DataValidationError(msg)
```

### 4. Frequency Array Validation

Add a standalone validation utility in `src/QDMpy/odmr/validation.py`:

```python
from loguru import logger

NV_FREQ_MIN_GHZ = 2.0
NV_FREQ_MAX_GHZ = 3.5

def validate_frequencies(frequencies: NDArray) -> None:
    """Validate frequency array for ODMR fitting.

    Checks finiteness and monotonicity (errors). Checks NV diamond range
    (warning only, since non-standard experiments exist).

    Args:
        frequencies: 1D or 2D frequency array in GHz.

    Raises:
        DataValidationError: If frequencies contain non-finite values or
            are not monotonically increasing.
    """
    if not np.all(np.isfinite(frequencies)):
        msg = 'Frequency array contains non-finite values'
        raise DataValidationError(msg)

    freq_1d = frequencies.ravel() if frequencies.ndim > 1 else frequencies
    if freq_1d.size > 1 and not np.all(np.diff(freq_1d) > 0):
        msg = 'Frequency array must be monotonically increasing'
        raise DataValidationError(msg)

    if freq_1d.min() < NV_FREQ_MIN_GHZ or freq_1d.max() > NV_FREQ_MAX_GHZ:
        logger.warning(
            f'Frequencies [{freq_1d.min():.3f}, {freq_1d.max():.3f}] GHz '
            f'are outside expected NV diamond range '
            f'[{NV_FREQ_MIN_GHZ}, {NV_FREQ_MAX_GHZ}] GHz'
        )
```

Note: The NV frequency range check is a **warning**, not an error, since
non-standard experiments may use different frequency ranges.

This function is called from `ODMRData.from_numpy()` (after Hz→GHz conversion)
and from `FitManager.__init__()` (on the frequency array).

## Backwards Compatibility

- **ODMRData**: Public API unchanged. `ODMRData(data=da)` and `ODMRData.from_numpy()`
  work identically. Code that previously passed invalid data will now get
  `DataValidationError` at construction instead of cryptic errors downstream.
- **FitResult**: Public API unchanged. `FitResult(parameters=..., ...)` works
  identically. `pixel_spacing <= 0` and empty parameters now raise immediately.
- **FitManager**: Public API unchanged. Empty data, frequency mismatches, and
  insufficient frequency points now raise `DataValidationError` at construction.
- **isinstance checks**: `isinstance(obj, ODMRData)` still works. `isinstance(obj,
  BaseModel)` will now also return True — this is unlikely to cause issues.
- **Serialization**: Pydantic adds `.model_dump()` and `.model_json_schema()` for
  free, but existing code doesn't use them, so no conflict.

## Rejection Alternatives

**Alternative: Use Pydantic models for ALL classes including FitManager.** Rejected
because FitManager is heavily stateful with mutable fit results, GPU state, and
caching. Pydantic BaseModel is designed for validated data containers, not stateful
managers. The hybrid approach (Pydantic for data containers, manual validation for
stateful classes) plays to each tool's strengths.

**Alternative: Keep manual validation, no Pydantic.** Rejected because the project
already depends on Pydantic (settings module), and `@field_validator` is cleaner than
scattering `_validate_data()` static methods. The declarative approach is easier to
maintain and extend.

**Alternative: Validate only in debug mode.** Rejected because dimension/coordinate
mismatches cause silent wrong results in production, which is worse than a validation
error.

**Alternative: Rely solely on xarray's implicit validation.** Rejected because xarray
catches some structural errors (e.g., missing dims in operations) but not all (e.g.,
wrong dim names, missing coordinates, non-numeric dtypes). Explicit validation
provides clearer error messages at the boundary.
